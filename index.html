Overview

What the shopper experiences, end to end

The experience we're building toward: a signed-in shopper opens Mia, gets a welcome menu, is guided through a product search, taps into a native PDP, checks their digigold balance, and can escalate to a live agent. The rest of this guide is how we deliver it in a WebView — phased, with guest discovery shipping first.

★ End-to-end shopper journey

The whole experience a signed-in shopper sees — from login, through Mia's welcome menu and a guided product search, to a native PDP, a digigold balance keyed on the verified identity, and escalation to a live agent. Colour tells you what's WebView (chat, buttons, carousel, balance, handoff) vs. native (login, home, PDP); each step is mapped to the section that implements it.

Full-size interactive version: open the shopper-journey mockup in a new tab ↗. The sections below are the developer-facing detail behind this flow.

Approach

Why a WebView — the integration path available today

The Tanishq iOS & Android apps talk to the shopper agent over Salesforce SCRT2 messaging. The rich replies — product carousels and suggestion chips — are drawn by Cimulate's closed copilot-widget bundle, which is web-only. Hosting that widget in a native WebView is the way to bring Mia to the mobile apps now.

◆ Why a WebView

Rendering the agent's rich replies is the expensive part of this problem — and that renderer exists only as a web bundle today. A native "messaging SDK" does exist, but it solves the wrong half: it moves messages, it doesn't draw carousels. So the fast, faithful way to launch is to reuse Cimulate's real renderer inside a WebView rather than rebuild it natively against an undocumented payload we'd then have to maintain.

"SDK" What it gives you What it does not
MIAW Mobile SDK (exists today) Transport only — SCRT2 connection, send/receive messages, push registration. No rendering. You would still build every carousel & chip natively.
Cimulate rendering SDK (not yet available) Transport + native rendering of Cimulate's rich replies — the eventual native path. Doesn't exist yet — depends on Cimulate's roadmap.
Because rendering is the expensive part, the transport-only SDK doesn't remove the hard work — it's the pipe, not the UI. Until a native rendering SDK ships, hosting Cimulate's existing web widget in a WebView is the only way to get the real carousels and chips without rebuilding and maintaining a renderer ourselves. This guide is that integration.
Not throwaway. When Cimulate ships a native rendering SDK, migrate to it for a fully-native experience — the native shell, the "Ask Mia" entry point, product-tap interception (§7), JWT verification (§10), and the push / resume plumbing (§11) all carry over unchanged.

Scope & phasing

The full experience ships in phases. Discovery is deliverable now; the authenticated and async-escalation phases gate on Salesforce-side capabilities (§10, §11), not on the app build.

Developer Guide

Embedding Mia in the Tanishq apps via WebView

Step-by-step integration for iOS & Android developers — the detail behind the journey above.

Scope: Discovery · authenticated loyalty actions · escalation to a human agent · case creation Out of scope: cart & checkout Approach: host Cimulate copilot-widget in a native WebView

Full scope stands. Discovery is deliverable now (~2 wks). Authenticated context/loyalty (§10) and async escalation resume (§11) depend on two Salesforce-side capabilities not in the current widget release — verified identity, then durable resume (§14 items 1 & 2). Every Tanishq-owned prerequisite runs in parallel, so those two are the only true gates. The WebView host is unchanged throughout.

01 How it works (architecture)

Native app (iOS / Android) └─ presents a full-screen WebView from an "Ask Mia" entry point └─ loads a tiny local HTML host page └─ <script> loads messaging.umd.js from cdn.search.cimulate.ai └─ calls CimulateMessaging.injectMessagingWidget(config) └─ widget connects to SCRT2 (guest OR verified) → Agentforce (Mia agent) └─ widget renders chat + product carousels + chips (all inside the WebView) └─ agent actions: loyalty lookups · create case · escalate to human Native app intercepts / assists: • product-URL taps in the WebView → cancel web nav → push native PDP • signed-in session → routing attributes + verified JWT (§10) • conversation continues with a human after escalation; push notifications for async replies (§11)

The widget is a closed, self-contained web bundle owned by Cimulate. It handles the SCRT2 connection, streaming, and all rich-reply rendering (carousels, chips). You do not parse SCRT2 payloads or render carousels yourself. Case creation and escalation are agent/MIAW behaviours — the widget already renders them; the native work is identity (§10), notifications, and lifecycle (§11), not new UI.

Reference implementation (web/SFRA): the plugin_commerce_client cartridge, file cartridge/templates/default/cimulate/messagingWidget.isml. The host HTML in §4 is the mobile equivalent of that template; §10 adds the session/verification handshake this cartridge uses.

02 Prerequisites

Org / platform (Salesforce admin / commerce team — confirm done)

  1. Agentforce + Messaging (SCRT2) configured in the core org, with an Embedded Service Deployment (Messaging for In-App/Web) whose channel routes to the Mia agent (Tanishq_Titan_Agent).
  2. MIAW user verification (signed JWT) configured on the deployment (public key/cert + claim mapping) — the deployment-side prerequisite for the verified-identity lookups (§10). Can be stood up in parallel with the Salesforce widget-side work it pairs with (§14, items 1 & 12). Guest mode covers discovery without it.
  3. Agent actions: loyalty API actions and an escalation / transfer-to-agent path (Omni-Channel + a queue of human agents) for §10/§11; a Create Case action for the case-creation flow (§11).
  4. CDN access to https://cdn.search.cimulate.ai from mobile clients (or use static-bundle mode — see §12).

App side

  1. An existing native PDP screen with a route that accepts a product ID / SKU (for §7).
  2. A place to launch the experience from (a tab or nav button — see §8).
  3. A custom-scheme asset handler (WKURLSchemeHandler / WebViewAssetLoader) to serve the host page over a real origin — not file:// (§5/§6, mandatory).
  4. Push notifications wired up (APNs / FCM) and device registration via the messaging API for async human-agent replies after escalation (§11; §14 item 2).

Get these from the Salesforce admin (they come from the Embedded Service Deployment). Field names match the widget's messagingConfig:

Two corrections from the mobile config review (17 Aug 2026):
  • capabilitiesVersion is not optional in practice. If omitted it defaults to the release-248 capability level, not "65" (which is release 258). Set it explicitly. At least "63" is required for action progress indicators — the "working…" state that makes loyalty lookups (§10) feel responsive.
  • cdnVersion is not a widget field — it's removed. On the web storefront this was an input to the SFRA cartridge that resolved which bundle to load; the widget itself never receives it. In a native app the host page does that job directly: the version segment in the <script src> URL is the pin, and static mode is just pointing that tag at a locally-bundled copy (§12). There is no key to pass.

04 Step 1 — Build the widget host HTML

This is the single asset both platforms load. Ship it in app assets and serve it over a custom scheme handler so it has a real https:// origin (see §5/§6 — do not use file://). It presents the widget as a full-bleed chat embed that fills the native container.

Use the chat embed, not the dialog. Setting componentConfig.type: "chat" renders the widget as an embed that fills its container and has no chat header or close button — so the native app's nav is the only header, and there's no close control that could strand the shopper in an empty WebView. This replaces the old "full-height dialog + hide the launcher + reconcile a doubled header" approach: the dialog is a floating panel (full-height ≠ full-width, and its header always carries a close button that can't be suppressed). The embed sidesteps all of it. (Resolves former open questions 2 & 3, and the §8 doubled-header question.)

    /* type:"chat" fills its container; the native app draws the header/nav. */

05 Step 2 — Host it in a WebView (iOS)

Use WKWebView. Inject the config at document-start, serve the host page over a custom scheme handler (not file://), and set a navigation delegate for product interception.

Do not load the host page from file:// (mandatory — mobile config review). A file:// document has no real origin, which makes browser storage, the cross-origin connection to SCRT2, and any embedded payment surface behave unpredictably and hard to diagnose. Instead register a WKURLSchemeHandler (e.g. app-assets://mia/host.html) that serves the bundled asset — the page gets a stable https-like origin with no network round-trip, so the "negligible" host-load cost in §9 still holds. Conversation resume (§11) also needs a stable origin to key storage on.
swiftimport WebKit

final class MiaViewController: UIViewController, WKNavigationDelegate, WKScriptMessageHandler {

    private var webView: WKWebView!

    // Supplied from remote config — never hardcode.
    struct MiaConfig {
        let scrt2Url: String; let orgId: String; let esDeveloperName: String
        let capabilitiesVersion: String; let logoUrl: String
    }
    var config: MiaConfig!

    override func viewDidLoad() {
        super.viewDidLoad()
        let cc = WKUserContentController()
        cc.add(self, name: "mia")                 // JS bridge (logging / events)

        // Inject config BEFORE any page script runs.
        let js = """
          window.__MIA_CONFIG__ = {
            scrt2Url: "\(config.scrt2Url)", orgId: "\(config.orgId)",
            esDeveloperName: "\(config.esDeveloperName)",
            capabilitiesVersion: "\(config.capabilitiesVersion)",
            logoUrl: "\(config.logoUrl)",
            routingAttributes: {}          // add NON-sensitive context here when authenticated (§10)
          };
        """
        cc.addUserScript(WKUserScript(source: js, injectionTime: .atDocumentStart, forMainFrameOnly: true))

        let wkCfg = WKWebViewConfiguration(); wkCfg.userContentController = cc
        wkCfg.allowsInlineMediaPlayback = true
        // Serve app assets over a real origin instead of file:// (see the warning above).
        wkCfg.setURLSchemeHandler(MiaAssetHandler(), forURLScheme: "app-assets")
        webView = WKWebView(frame: .zero, configuration: wkCfg)
        webView.navigationDelegate = self
        webView.scrollView.bounces = false            // reduce the "web scroll" tell
        view.addSubview(webView)                        // pin with your layout / safe area

        // Custom-scheme URL → served from the bundle by MiaAssetHandler (no network hop).
        webView.load(URLRequest(url: URL(string: "app-assets://mia/host.html")!))
    }

    // Product-tap interception — see §7.
    func webView(_ webView: WKWebView, decidePolicyFor a: WKNavigationAction,
                 decisionHandler: @escaping (WKNavigationActionPolicy) -> Void) {
        guard let url = a.request.url else { decisionHandler(.allow); return }
        if let pid = ProductURLParser.productId(from: url) {
            decisionHandler(.cancel)                    // don't navigate the WebView away
            navigateToNativePDP(productId: pid)         // your existing PDP route
            return
        }
        decisionHandler(.allow)
    }

    func userContentController(_ c: WKUserContentController, didReceive m: WKScriptMessage) {
        // Handle {type:"log"} and any future widget events posted from JS.
    }
    private func navigateToNativePDP(productId: String) { /* push ProductViewController */ }
}
injectionTime: .atDocumentStart guarantees __MIA_CONFIG__ exists before the host script reads it. MiaAssetHandler is a small WKURLSchemeHandler that reads host.html (and, in static mode, messaging.umd.js) from the app bundle and returns them with a text/html / application/javascript content type — no network hop, real origin. The widget bundle still comes from the CDN unless you use static mode (§12).

06 Step 3 — Host it in a WebView (Android)

Use android.webkit.WebView. Enable JS + DOM storage, inject config, serve the asset via WebViewAssetLoader (a real https origin, not file:///android_asset/), and override URL loading.

Do not load from file:///android_asset/ (mandatory — mobile config review). Same reason as iOS: a file:// page has no true origin, so DOM storage, the SCRT2 cross-origin connection, and conversation resume (§11) are unreliable. Use androidx.webkit.WebViewAssetLoader to serve the bundled host page under an https://appassets.androidplatform.net/… origin — assets are read locally (no network hop) but the page gets a stable origin.
kotlinclass MiaFragment : Fragment() {

    data class MiaConfig(
        val scrt2Url: String, val orgId: String, val esDeveloperName: String,
        val capabilitiesVersion: String, val logoUrl: String)
    private lateinit var config: MiaConfig       // from remote config — never hardcode

    @SuppressLint("SetJavaScriptEnabled")
    override fun onViewCreated(view: View, s: Bundle?) {
        val webView = view.findViewById<WebView>(R.id.mia_webview)
        webView.settings.apply {
            javaScriptEnabled = true
            domStorageEnabled = true                    // widget needs web storage
            mediaPlaybackRequiresUserGesture = false
        }

        webView.addJavascriptInterface(object {
            @JavascriptInterface fun log(msg: String) { Log.d("Mia", msg) }
        }, "MiaBridge")

        // Serve bundled assets under a real https origin (no network hop).
        val assetLoader = WebViewAssetLoader.Builder()
            .addPathHandler("/assets/", WebViewAssetLoader.AssetsPathHandler(requireContext()))
            .build()

        webView.webViewClient = object : WebViewClientCompat() {
            override fun shouldInterceptRequest(v: WebView, req: WebResourceRequest): WebResourceResponse? =
                assetLoader.shouldInterceptRequest(req.url)

            override fun onPageStarted(v: WebView, url: String?, f: Bitmap?) {
                v.evaluateJavascript(
                    """window.__MIA_CONFIG__ = {
                        scrt2Url:"${config.scrt2Url}", orgId:"${config.orgId}",
                        esDeveloperName:"${config.esDeveloperName}",
                        capabilitiesVersion:"${config.capabilitiesVersion}",
                        logoUrl:"${config.logoUrl}",
                        routingAttributes:{} };""", null)   // add context when authenticated (§10)
            }
            // Product-tap interception — see §7.
            override fun shouldOverrideUrlLoading(v: WebView, req: WebResourceRequest): Boolean {
                val pid = ProductUrlParser.productId(req.url)
                return if (pid != null) { navigateToNativePDP(pid); true } else false
            }
        }
        // host.html + (static mode) messaging.umd.js live under src/main/assets/mia/
        webView.loadUrl("https://appassets.androidplatform.net/assets/mia/host.html")
    }
    private fun navigateToNativePDP(productId: String) { /* navigate to your PDP */ }
}
onPageStarted injection is a pragmatic default. If the host script races ahead of the config, load the host HTML as a string with the config <script> prepended, or gate injectMessagingWidget on a config-ready poll. WebViewAssetLoader comes from the androidx.webkit library.

07 Step 4 — Intercept product taps → native PDP

This is the only non-trivial native glue in the discovery phase.

Tap in carousel → WebView tries to navigate to a product URL → native interceptor recognizes it, cancels the web nav → native PDP opens with the product ID (back returns to chat)

Both platforms call a shared parser that recognizes a product URL and extracts the ID:

pseudocode// Product URL shape (EXAMPLE — verify against a real tap):
//   https://www.tanishq.co.in/shop/p/aveer-gold-diamond-ring/513872
// Rule: path contains "/p/" and the last non-empty segment is the product id.

func productId(from url) -> String? {
    guard host is a Tanishq domain   else return nil
    guard path contains "/p/"       else return nil
    let id = lastPathComponent
    return id.isProductIdShaped ? id : nil
}
Confirmed (mobile config review): on tap the widget performs a normal same-frame link navigation to the product page URL — not a JS event or postMessage. The delegate hooks in §5/§6 see it, so the interception design works as drafted. The product URL comes from the agent's response payload and points at the storefront, so the /p/ + last-segment rule below describes that storefront URL scheme, not the widget's — validate it against a real tap and keep the parser app-side.

Cases that silently bypass the interceptor

  • openLinksInNewTab must stay false (its default, set in §4). If enabled, taps open in a new window that does not reliably reach shouldOverrideUrlLoading (Android) or the navigation delegate (iOS) — interception silently fails.
  • Cart management enabled on the deployment changes the tap entirely. If the messaging deployment has cart management on, a product tap stops being a link navigation and instead drives the conversation to an in-chat product detail view — the delegate never fires and there is nothing to intercept. This flips the whole §7 design, so confirm whether cart management will be enabled before building the interceptor (§14, item 18). Mia's launch scope is discovery-only (no cart / checkout), so it should be off — but verify it on the actual deployment.
  • Embedded express-payment surfaces need a real page origin. Any express-payment surface the widget may render requires a true https origin to work — a further reason to serve the host page over a custom scheme handler rather than file:// (§5/§6). This is not a case to route to the native PDP; it's a reason the §4.1 origin rule is mandatory.

Decisions to lock

  • Fallback for products not in the native catalog. Open the URL in an in-app browser (SFSafariViewController / Chrome Custom Tabs), not the system browser — keeps it contained.
  • Back behavior. Native back returns to the WebView; keep the VC/fragment alive so the conversation + scroll state are retained.
  • If URL matching proves brittle, a component-override mechanism (overridesUrl, §15) can let a product tile call the native bridge directly — a cleaner contract than URL parsing. Ask Cimulate for the override hook shape (§14).

08 Step 5 — Make it feel native (not a floating web widget)

The difference between "native chat feature" and "bolted-on web page" is mostly configuration + presentation. With type:"chat" (§4) most of it is already handled:

The web layer will not handle it.

09 Performance & latency

WebView latency splits into two buckets. Cold start is visible and worth engineering for; steady-state rendering is a non-issue for a chat + carousel. Critically, the largest single delay — the agent's first response — is SCRT2 + Agentforce round-trip that every option pays, WebView or fully native.

Cold start — the "tap → usable chat" gap (stacks)

StageTypical costNotes
WebView process spin-up~50–300 msFirst WebView of the session is slowest
Load host HTML~0 msNegligible — served from app assets via the custom scheme handler (§5/§6), no network hop
Download messaging.umd.js from CDN~200 ms–1.5 s+The dominant variable — bundle size × network × CDN edge
Widget init + injectMessagingWidget~100–400 msJS parse/exec + mount
SCRT2 connect + first agent turn~0.5–2 sShared by all options (native too) — not a WebView cost

Realistically ~1–3 s to an interactive chat on a cold start, dominated by the CDN bundle fetch. Warm/repeat opens are far faster.

Steady state — not a real problem here

This experience is text bubbles, a horizontal image scroller, and chips — trivial for a modern WebView. You won't hit the scroll-jank associated with heavy DOM/video pages. The one thing to watch is carousel image loading, which is network latency (identical to a native list), not rendering.

Mitigations — make cold start feel instant

  • Bundle the widget locally (static mode). Biggest single win — removes the CDN fetch from the critical path (and drops the CDN runtime dependency + CSP allowlist). Point the <script src> at a bundled copy of the pinned bundle instead of the CDN (§12); get the bundle from Cimulate.
  • Pre-warm the WebView. Create the WebView and load the host HTML before the user taps (e.g. when the parent tab appears), so injectMessagingWidget has already run by the time they open Mia.
  • Pin & cache the CDN version. If you can't go static, pin the version segment in the <script src> URL (§4) so the bundle is HTTP-cacheable — the 2nd open is much faster than the 1st.
  • Native skeleton during load. Show a native splash/skeleton for the ~1–2 s window. The native frame is already on screen, so perceived latency stays low.
  • Keep the instance alive. Don't destroy the WebView on back — retain the VC/fragment (§7) so re-opening is instant and conversation state survives.
Bottom line: the cold-start CDN fetch is the only WebView-specific latency, and static-mode + pre-warming largely neutralize it. Steady-state rendering is a non-issue, and the dominant agent-response latency is identical whether Mia runs in a WebView or a fully native shell.

10 Authenticated context & hidden pre-chat variables

In scope. Authenticated context and hidden pre-chat variables are part of the target experience — the personalised greeting and the digigold / order / tier lookups. Hidden pre-chat context (routingAttributes) works in the current widget today. The verified-identity half has a Salesforce-side dependency (see the warning below) that must be lined up in parallel so it lands with the rest — the app-side prerequisites don't wait on it.
Critical-path dependency (mobile config review, 17 Aug): the current widget release establishes messaging sessions as an unauthenticated shopper only — there is no config field or method to hand it a signed JWT yet, so a conversation can't be bound to a verified customer through the widget today. The platform capability exists — the Enhanced Chat API's generateAccessTokenForAuthenticatedUser is the authenticated counterpart to the unauthenticated call the widget currently makes — so this is Salesforce work to close, and it gates the verified-identity lookups. Track it as item 1 in §14; the app-side pieces (JWT minting service, deployment config) proceed in parallel. Do not ship digigold/loyalty keyed on a routing attribute as an interim workaround — that's the exact IDOR the rule below prohibits; defer the lookup rather than weaken the identity model.

Some Tanishq use cases need the agent to act on the signed-in shopper — e.g. reading their digigold balance, order history, or loyalty tier by calling Tanishq APIs. The agent gets that context two ways, and they are not interchangeable:

Two jobs, two mechanisms — don't mix them up

JobMechanismTrust
Identity & authorization
whose balance may we fetch		 MIAW user verification — the app sends a signed JWT, signed server-side by Tanishq's backend with the key/cert registered on the Embedded Service deployment. Salesforce verifies the signature before the agent trusts the identity. Trusted — agent derives the customer from the verified identity
Context & personalization
name, city, tier, current page		 Hidden pre-chat fields → messagingConfig.routingAttributes Spoofable — set on the client. Convenience only.
The one rule that matters: hidden pre-chat fields are set in the client, so they can be tampered with. Never let a client-supplied field decide which customer's private data to return — a plain userId in routing attributes is an IDOR (any client could request someone else's digigold balance). Sensitive lookups must key off the verified JWT identity, not a routing attribute.

How context flows in the WebView model

Native app (holds the authenticated session + can request a signed JWT) ├─ IDENTITY: gets a signed JWT from Tanishq backend → passes to widget's user-verification hook │ → Salesforce verifies signature → agent trusts the customer └─ CONTEXT: injects non-sensitive details into the WebView (same __MIA_CONFIG__ pattern) → host HTML sets them as messagingConfig.routingAttributes → widget → SCRT2 → Agentforce sees them as conversation variables → agent action calls Tanishq API keyed on the VERIFIED identity → digigold balance
Timing: both the verification token and routing attributes must be set before the conversation connects. Inject at document-start and pass them into injectMessagingWidget — not after the chat is open.

Wiring routing attributes (context)

Extend the host config with a routingAttributes object and pass it through. Keep it to non-sensitive personalization:

js// in mia_host.html — merge into the injectMessagingWidget call (§4)
messagingConfig: {
  scrt2Url: cfg.scrt2Url, orgId: cfg.orgId,
  esDeveloperName: cfg.esDeveloperName,
  capabilitiesVersion: cfg.capabilitiesVersion,
  routingAttributes: cfg.routingAttributes || {}   // e.g. { firstName, city, loyaltyTier } — NON-sensitive
}

Native side just adds the object to the injected config (§5/§6). iOS:

swift// context only — safe to be client-set; do NOT put anything that authorizes data access here
let attrs = """{ "firstName":"\(user.firstName)", "loyaltyTier":"\(user.tier)" }"""
let js = """window.__MIA_CONFIG__ = { /* ...§5 fields... */,
    routingAttributes: \(attrs) };"""
cc.addUserScript(WKUserScript(source: js, injectionTime: .atDocumentStart, forMainFrameOnly: true))

Wiring identity (verification) — required for sensitive data

  1. Tanishq backend signs a JWT for the signed-in user (server-side, with the private key). The app fetches this token — it never signs client-side.
  2. Salesforce admin registers user verification on the Embedded Service deployment (the public key/cert + subject/claims mapping). This is the piece we need to confirm exists — see §14.
  3. The native host hands the token to the widget's user-verification hook before connect. This hook does not exist in the current widget release (mobile config review) — it's the Salesforce-side gap tracked as item 1 in §14, expected to surface the Enhanced Chat API's generateAccessTokenForAuthenticatedUser path. The steps above/below (backend signing, deployment config) can be built now so this drops in when available.
  4. The agent's Apex/Flow action reads the verified customer identity and calls the Tanishq digigold API with it. Routing attributes may add context, but the customer key comes from the verified token.
Token hygiene: use short-lived JWTs, refresh on expiry, and re-issue on account switch / logout so a stale token can't bind the chat to the wrong user.

11 Escalation to a human agent (MVP) & case creation (Phase 2)

Scope flag: both handoff and case creation are agent + MIAW platform behaviours, not widget features you build — the widget already renders them in-chat. Escalation to a live agent is MVP (the "Talk to an agent" journey step); its only real native work is notifications and lifecycle — keeping the conversation alive when a human replies minutes or hours later. Case creation is Phase 2.

Escalation to a human — the one real mobile problem: async replies

Works today (mobile config review): the in-chat escalation control (enabled via enableEscalationToAgent, §4, and an escalation topic on the agent), and rendering of the handoff itself — the widget shows participants joining/leaving, typing indicators, and routing failures, and continues the same thread with a human agent. (No queue-position display.) Handoff within a living session needs no native work.

When the agent hands off, the conversation transfers via Omni-Channel routing to a queue of human agents (in the Service Console). The widget shows the transfer and continues the same thread. The catch is timing:

A human doesn't reply instantly. The shopper will background the app or close the WebView while waiting. Unlike the bot, the agent's reply can land minutes or hours later — so you cannot rely on the WebView being open. This is the defining requirement of the escalation MVP.
Shopper asks for a human → agent escalates → Omni-Channel routes to a queue → shopper backgrounds the app while waiting → human replies later → push notification (APNs / FCM) → shopper taps → app reopens the WebView, widget resumes the SAME conversation → human reply shown
What does NOT work today (mobile config review):
  • The conversation does not survive the WebView being destroyed. Continuity relies on per-session browser storage, so it holds while the app is merely backgrounded — but a cold start after a push begins a NEW conversation rather than resuming. Conversation identity isn't keyed to anything the app controls, which is the underlying reason. Durable resume is expected to follow from the verified-identity work in §10 (it needs a stable identity to key on) — so this depends on that Salesforce delivery (§14, item 2).
  • The widget performs no push device registration. Registering a device token is native-side work against the messaging API — endpoint registerDeviceForPushNotifications. How registration attaches to a widget-owned conversation is still an open item (§14, item 3).

What this requires

  1. Push notifications for messaging. Configure MIAW push (APNs on iOS, FCM on Android) and register the device token via registerDeviceForPushNotifications — native-side, not the widget. Confirm how registration binds to the widget's conversation (§14, item 3).
  2. Durable conversation resume. Reopening — especially a cold start from a push — must reconnect to the same conversation, not start fresh. Not available today; gated on the stable-identity work in §10 (§14, item 2).
  3. Tap-through routing. A messaging push should deep-link straight into the Mia WebView (reopened to the live conversation), not the app home.
  4. Presence / lifecycle. Keep the messaging session valid across background/foreground; don't tear down the conversation when the WebView is dismissed (retain it as in §7, or rely on server-side session + resume).
Honest status: in-session handoff works now; async replies across app restart are the least-proven piece and are blocked on Salesforce delivery of durable resume (which is expected to build on §10's verified identity). The §11 caveat stands — resolve items 2 & 3 in §14 before committing dates. Push credentials, Omni-Channel queue, and device registration are app/admin prerequisites that can proceed in parallel.

Case creation (Phase 2) — mostly config, little native work

The agent creates a Salesforce Case via an Agentforce action (Apex/Flow) when the shopper asks for help ("my order hasn't arrived"). It can pre-fill the case from the verified identity (§10) — contact, order, loyalty tier. In the WebView this needs no native code: the agent runs the action and the widget renders the confirmation.

  • Case → native deep link (optional). If the agent returns a link to view the case ("track your request"), route it through the same URL interceptor as product taps (§7) and open a native "My Requests" screen instead of a web page.
  • Attachments — not currently supported. The messaging experience has no in-chat file/attachment UI today (mobile config review), so a photo-attachment use case (e.g. a damaged item) is out of scope for now — it's a roadmap item (§14, item 5). Don't design a Case flow that depends on it yet.

  • iOS ATS: all HTTPS, so default ATS is fine. Only add a host-scoped exception for a sandbox custom/self-signed cert.
  • Android: HTTPS works out of the box. For a cleartext/private-CA sandbox, add a network-security-config scoped to that host only — never global.
  • Static-bundle alternative: "static mode" is not a widget flag — it's simply pointing the host page's <script src> at a locally-bundled copy of messaging.umd.js (served via the same custom-scheme handler as the host page, §5/§6) instead of the CDN. 13 Testing checklist

Discovery — deliverable now (§1–§9)

  • Widget loads and connects (guest) — welcome message from Mia appears.
  • Free-text query returns a product carousel; horizontal touch scroll works.
  • Chips / suggestions render and are tappable; tapping sends the follow-up.
  • Tapping a product opens the native PDP with the correct product (not a web page in the WebView).
  • Back from PDP returns to the same chat state (conversation + scroll retained).
  • Product not in native catalog → falls back to in-app browser, not the system browser.
  • Full-screen presentation: no floating FAB, native nav present, safe-area respected.
  • Keyboard: composer stays visible when focused (both platforms).
  • CDN blocked / offline → graceful failure (logged via bridge), app doesn't hang.
  • Dev / stage / prod config swap works via remote config (no rebuild).
  • Theme matches Tanishq brand (colors, header, fonts) end-to-end.

Authenticated & loyalty (§10) — once verified identity lands (§14 item 1)

  • Signed-in shopper: verified JWT is accepted; agent greets by the verified identity.
  • Loyalty action (e.g. digigold balance) returns the correct signed-in user's data.
  • Tampered / spoofed routing attribute cannot retrieve another user's private data.
  • Token expiry / account switch / logout re-issues the token; chat rebinds correctly.

Escalation to a live agent (§11)

  • Works now: escalation transfers to a human; participants/typing/routing-failure render; the same thread continues in the widget.
  • Works now: conversation survives background/foreground while the WebView is alive.
  • Blocked on §14 items 2 & 3: app backgrounded → human replies later → push notification arrives (native registration).
  • Blocked on §14 item 2: tapping the push after a cold start reopens the WebView to the SAME conversation (not a fresh chat).

Case creation (§11)

  • Agent creates a Case, pre-filled from the verified identity; confirmation renders in-chat.
  • "View my request" link opens the native requests screen (not a web page).
